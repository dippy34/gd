# OBSIDIAN CHOIR — handoff

**`OBSIDIAN-CHOIR.gmd` in this folder is the level, reverted to how it was before
any decoration work.** 12,613 objects: the gameplay layout and almost nothing
else. Import it with GDShare. That is the thing to build on.

Everything else here is material: what the layout is, what was already measured,
tools that work, and the mistakes already paid for.

---

## 1. The level

* **Song**: Xtrullor — Supernova, Newgrounds **593661**, 170 BPM, offset 0.
  First beat at t = 0.134 s; an 8-beat phrase is 2.824 s.
* **Length**: x 25 → 20,084. About 59 seconds.
* **Route** (`level/route-and-beats.json` has the exact numbers):

| time | x | mode |
|---|---|---|
| 0:00 – 0:22.7 | 0 – 5,707 | cube, half speed |
| 0:22.7 – 0:28.4 | 5,707 – 7,466 | wave, 1× (teaser) |
| 0:28.4 – 0:34.0 | 7,466 – 8,885 | cube, half speed (build) |
| 0:34.0 – 0:56.6 | 8,885 – 19,456 | **wave, 3× — the drop** |
| 0:56.6 – 0:59 | 19,456 – 20,084 | cube landing |

The wave sections are an enclosed corridor made of 12,062 15-unit squares on a
45° staircase, spanning y 0 – 360. The cube sections are nearly empty: ground at
y = 15, a handful of spikes, rings at y = 65.

`level/layout.level` is the raw level string. `level/layout-map.png` is a map of
the geometry.

## 2. Rules that must hold

The user's layout is finished and must not change.

1. **Never add, remove, move or resize a gameplay object.** `tools/verify_aurora.py`
   diffs the built level against `level/layout.level` and must report
   `missing 0, changed/added 0`.
2. **Every decoration object gets `121 = 1` (no touch) and `134 = 1` (passable).**
   That makes it harmless whatever its id.
3. **Never use a hazard or interactive id as decoration** — spikes, saws, fire,
   portals, pads, orbs, speed changes. `passable` does *not* disable a spike's
   kill box. The exclusion list is in `tools/verify_aurora.py`.
4. **Nothing opaque in front of the gameplay.** Additive glow over the corridor is
   fine and looks good; an opaque shape at z ≥ 1 hides the path.
5. Never put a gameplay object in a Move or Rotate group.

## 3. The camera — read this before placing anything

This cost a whole revision. GD's camera shows about **330 units vertically**, and
it is *not* centred on y = 180.

* cube parts: centre y ≈ **95** → visible band roughly **−70 … 260**
* wave parts: the camera rides the corridor, centre **68 … 280** depending on x

`tools/cam.py` computes `cam_y(x)` from the layout itself. Anchor everything to
it. A first version hung its sky between y 400 and 680; the player only ever saw
the bottom edge of it.

```python
from kocmoc_terrain import Terrain
import cam
cam_y = cam.make(Terrain())      # cam_y(x) -> centre of the visible band
```

## 4. You can actually look at your work

The full Geometry Dash sprite atlases ship with the game on this machine:

```
~/Library/Application Support/Steam/steamapps/common/Geometry Dash/Geometry Dash.app/Contents/Resources/GJ_GameSheet*.plist / .png
```

`tools/render.py` reads them, resolves colour channels through `kS38` including
copy-chains and colour triggers, applies each object's HSV value multiplier,
honours z-layer / z-order and additive blending, and composites to PNG.
`tools/shot.py` renders through the camera model above and tiles the results.

```bash
cd tools
/usr/bin/python3 shot.py ../versions/v2-aurora.level check "[300,3150,8950,12000,17750]" 2
```

Use `/usr/bin/python3` for anything that renders — it has numpy and PIL. The
uv python does not.

Looking at it is what caught every real problem. The statistics never did.

Known gaps in the renderer: ids 1886/1887/1888 (the glow orbs) use `emptyFrame`
and `emptyGlow`, which are literally empty files, so it substitutes a synthesised
radial disc; the 3D-line pieces (507/508/512-514/578/579/584-587/597) and some
outline ids are generated by the game and get stand-ins.

## 5. What was measured off KOCMOC UNLEASHED

`research/kocmoc-unleashed-109381612.level.gz` is the real level — "KOCMOC
UNLEASHED hol", id 109381612, 112,518 objects, pulled from the game's own
download endpoint. It is the fullest copy that exists publicly; the original by
cherryteam was never uploaded. Ungzip it before using the analysis scripts.

`research/report_A.txt` is the full statistical dump. `research/vocab.txt` is its
220-id vocabulary with per-id scale bands, rotation rates and z-layers. The `.py`
tables are quantile data generated from it:

| file | what |
|---|---|
| `idlum_table.py` | per-sprite luminance quantiles for 244 ids |
| `joint_table.py` | luminance quantiles per footprint band |
| `scale_table.py` | per-sprite scale quantiles for 322 ids |
| `shape_table.py` | per-sprite rotate / stretch / flip rates |
| `lum_table.py` | overall luminance and footprint quantiles |

The facts that turned out to matter:

* **43.8% of KOCMOC is effectively invisible** — resolved luminance ≤ 0.03.
  Those are opaque black masks that carve shapes out of the light behind them.
  Its *median* object sits at 0.047.
* **Brightness belongs to the sprite.** Star sprites (3625) are bright 86% of the
  time; small balls (1764) are ink 90% of the time; 3D-line pieces sit mid.
* **Big shapes are dark. Only small ones are allowed to be bright.**
* Its starfield is 3625 at scale **0.051**, all on one colour channel, with a
  median nearest neighbour of **3.2 units** — packed into tight clumps, not
  spread evenly.
* 48% of its objects are rotated, 62% of those off-axis; 37% anisotropic; 17%
  skewed; median nearest neighbour 2.1 units; ~99 objects per 30-unit column.
* It drives ~274 colour channels with 685 colour triggers, so the palette moves
  while you play. Its look is black / white / grey with rare blue and gold.

Verified separately: the Fandom and official wikis describe it as black, white
and greys, black-hole shaped decorations, and frequent flickering.

## 6. What was tried, and what the user said

**v1 — `versions/v1-kocmoc-statistical-78k.gmd`.** Generated decoration by
rank-matching every measured distribution from KOCMOC: luminance, footprint,
per-sprite brightness, transform rates. The histograms matched almost exactly.
The user's verdict: *"Wow. That's really bad."* Statistics do not compose. The
level was correct noise.

**v2 — `versions/v2-aurora-designed-60k.gmd`.** Placed by hand-written rules
instead: black frame, near-black corridor with a neon outline and a soft halo
traced along its real silhouette, one idea per screen, a colour journey (pale
blue → ice → indigo → white at the drop → violet → gold → warm white), set-pieces
on the beat. Went 43k → 81k → 60k objects across three passes. Better, but the
user found it getting too complicated and asked to revert.

Their feedback, in order, worth keeping:

* don't paste generated batches — decode a real level's technique first
* a lot of the decoration was above the camera; only its bottom was visible
* object count is a goal, never a requirement — *"if you can't make it good with
  that many objects, then don't use that many"*
* they want black-hole effects and a Kocmoc-like star background
* keep it simple

`tools/design.py` and `tools/effects.py` are v2's source if any of it is useful —
the silhouette tracer, the camera model, the black hole, eclipse, pulsar, warp
tunnel, aurora, rift, orbiters and comet routines all work. Take what helps and
throw away the rest.

## 7. Traps already paid for

* **Parsing a `kS38` colour entry by `split('_6_')` is wrong.** Any RGB component
  equal to 6 creates a false match and the channel silently vanishes, rendering
  white. Split on `_` and zip the pairs. Three palette channels disappeared this
  way and the whole build looked blown out until it was found.
* **Rank-matching footprint globally blows small sprites up.** Match per sprite id.
* **`emptyFrame` / `emptyGlow` are empty files** — the glow orbs are drawn by the
  game, not from the atlas.
* **A gradient sprite at small scale reads as a hard grey rectangle.** Keep
  gradients at scale ≥ 2 or they look like debris.
* The 3D-line and outline ids (507, 508, 468, 472, 1338, 1339, 1835 …) have no
  atlas sprite; names came from flowvix's gd-info-explorer.
* Level ids 3636 / 3637 (`d_circle_01/02`) are **not** attested in any reference
  level on disk. Circles were built from glow orbs instead.

## 8. Running things

```bash
cd tools
python3 design.py                 # rebuild v2 into ../versions/
python3 verify_aurora.py          # the safety and integrity checks
/usr/bin/python3 shot.py ../versions/v2-aurora.level out "[300,8950,17750]" 2
gunzip -k ../research/kocmoc-unleashed-109381612.level.gz   # before analyse/mine/lumen
```

Renders land in `tools/shots/` — the directory has to exist, it is already here.
`verify_aurora.py` uses `gmdkit` for an independent round-trip check if it is on
the path; that one line is optional and everything else runs without it.
